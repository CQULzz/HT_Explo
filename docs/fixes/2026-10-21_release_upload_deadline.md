# 完整数据上传的慢连接重试

阶段43实际发布时，两个512MiB分卷的gh进程分别已持续约313秒与217秒，仍只读取约64MB/49MB；当时总发送速率约0.25MiB/s。TCP状态显示连接存在重传。没有证据把全部网络原因归结为某一个设备或服务。

核实两个进程确实属于本轮发布器、对应远端资产尚未出现后，仅结束这两个gh子进程，让发布器原有重试重建连接；已完成的分卷未重传，原始目录未改。之后观测到总发送速率约11MiB/s，剩余分卷完成上传。这个事实不能保证所有网络条件下重试都能提高速度。

为避免后续单次上传无限等待，`publish_streamed_ht_trial.py`新增`--upload-timeout-seconds`，默认180秒。每个资产最多沿用原4次尝试；超时由subprocess终止所属gh，重新检查远端后再试。同名不同内容仍拒绝覆盖，失败仍保留本机资料。较慢的稳定网络可以显式增加此参数；重试耗尽要标待上传，不能写成功回执或清理源文件。

验证：`python3 presentations/test_streamed_release_retries.py`，1项端到端本地CLI桩测试通过（约1.9秒）：首个上传故意挂起并超时，随后重试、校验全部资产、生成完整回执，逐文件确认源目录原样保留。测试只使用临时Git仓库和本地gh桩，不访问GitHub，也不伪称真实600秒实验。正在进行的实际上传使用其启动时载入的旧代码和人工定向重试；新超时路径的网络效果尚未另外实测。

本修正只影响数据传输工具，不改变导航、HT、地图或控制行为，不另算一轮导航600秒候选。
