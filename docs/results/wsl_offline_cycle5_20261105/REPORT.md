# 循环5：前沿继续选择资格与无效窗口修复

本轮承接循环3的剩余队列修复及循环4可选建图调度，基线ec1a145。按用户要求仍不运行仿真/回放/实车，不创建Release。下面都是离线反例与旧数据诊断，不产生新的探索量/源龄成绩，不宣称全局验收通过。

## 问题与证据

生产SelectViewPoint的前沿入队/首次选择门限为15，但第一项选择后先用表面门限40决定是否停止。收益15..39的其他合格前沿会因此漏选。新增同一生产选择器测试覆盖4个种子(0,1,42,99)×4个收益(14,15,39,40)，分别核对低于门限不选、合格的两个不重叠目标都恰好选一次。原实现中15和39这8个参数组合失败；14和40控制通过。另一个表面控制检查仍要求40，39不选，防止意外降低表面门限。

参数kGreedyViewPointSampleRange=0/-1在原构造器不报错，却可使后续uniform_int_distribution的[0,range-1]成为无效区间。新增构造边界测试确认原实现未拒绝；正窗口1和默认3应保持可用。本轮不实际调用无效分布制造崩溃。

修复前3项新增GTest中2失败（前沿、非正窗口）、1控制通过，日志before_regression.log。测试内容哈希在PROVENANCE，前后断言未变。

## 代码修改

local_coverage_planner.cpp以任务类别选择既有min_gain：前沿15、表面40；剩余队列只用该门限决定继续，移除重复/错误的40点前置判断。构造时拒绝非正采样窗口。默认窗口3、随机流、TSP/目标策略、HT阈值/未知/时效/几何保护及配置未改。循环3对queue_copy剩余收益的修复保留，本轮不修改建图候选。

## 验证

源码和测试位置沿用已有local_sampling_test，测试fixture支持窗口覆盖。重建通过（既有signedness警告），完整9组CTest通过，98.31s；本组包含2种子、2剩余收益、5完成/未知、2前沿/表面、1窗口共12个GTest。16组前沿参数、2组表面及4个窗口边界检查全部通过。完整几何/地图过期/输入/启动/返航控制回归通过，原始构建与CTest日志保留。环境为WSL Ubuntu-24.04/ROS2 Jazzy、独立build_real/install_real、测试域229，命令及候选/测试/二进制SHA256见PROVENANCE。

这些检查证明指定选择器反例被修复，不能证明所有未知场景的完成判断或任何闭环性能。此前组合候选曾源龄失败，拆开修复与单元通过不能把失败改称通过；仍须后续同种子120秒对照，本轮没有执行。

## 几何停车的只读核对

旧queue_seed99_c04录包按接收记录顺序，将碰撞云与最近收到的里程计配对。末段最近有效高度障碍点约(0.6400,-3.5560,-0.3515)，车体参考约(1.2000,-4.1054,-0.6058)，水平距离0.78450m，dz约0.2543m。现有规则为margin0.7 + 0.2×0.2格的半对角线，即半径0.84142m，高度±0.5m，该测量确实落入现有包络。因此这不是仅凭状态字符串发现的“空云误报”，没有证据可安全删除几何拦截。

GEOMETRY_EVIDENCE保留最近10对记录、原始路径及配置/代码SHA，inspect_recorded_geometry.py可只读重算。记录器接收顺序并不等同跟踪器回调顺序，测量云也不等同独立场景真值；不能据此判断实际车身已碰撞、确定误检原因或证明安全脱困路线。源龄、制动/重规划时序可能相关，但尚未证实。保持安全停车，后续检查避免进入阻塞位置的规划/反应策略，不以缩小保护半径换取运行。
