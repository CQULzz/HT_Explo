# HT逻辑能否实车运行：代码评估

结论：**按本仓库默认实车入口，不能直接构成可工作的实车闭环。核心高程→HT→XYθ规划→跟踪逻辑具备移植基础，但存在已确认的数据链路缺口与时序问题，尚不能判定当前程序具备完整实车运行条件。** 这是代码与离线测试结论，不以仿真效果推断实车可用。

用户明确要求不做仿真实验后，已停止此前启动的实验，清理记录 `remaining_live_descendants=[]`。记录状态为INTERRUPTED，未完成600秒；不作为实车或完整仿真验证，不继续发布实验结果。本评估不启动传感器、车辆、仿真或任何速度输出节点。

## 已确认的运行阻碍及修正方案

| 项目 | 代码证据与影响 | 修正方案与验证边界 |
|---|---|---|
| 默认定位输入不兼容 | `config/fixposition.yaml`使用sensor_short，驱动明确以best-effort发布；TARE用默认reliable订阅。离线`qos_check_compatible`返回ERROR，默认组合不能匹配 | 统一定位消息发布/订阅的可靠性设置。可让订阅接受传感器QoS，或明确让驱动可靠发布；不是仅改话题名。尚未修改实车配置，避免擅自决定消息策略 |
| 雷达原始数据不等于算法输入 | 雷达配置发布`/rslidar_points`、frame=rslidar；规划器订阅`/registered_scan`，回调只接受map或/map坐标。实车launch只启动驱动和TARE，没有点云定位/配准转换节点 | 提供真实时间戳下的去畸变/坐标转换链路，生成地图系点云。不能仅将话题或frame_id改名冒充已转换坐标。是否已有外部节点尚未知 |
| 里程计源未贯通 | 实车launch只将TARE改为`/fixposition/odometry_enu`；follower硬编码订阅`/state_estimation`，HT桥接的默认表面参考里程计同样是`/state_estimation` | 统一三者使用的里程计及坐标参考点，或显式配置/重映射；不能只改规划器。外部是否另有重发布器尚未知 |
| 实车入口没有启动完整计算链 | `explore_ht_fixposition.launch.py`没有启动高程建图、cupy_to_ht或xytheta_follower。缺少高程/HT图时ready=false；缺少跟踪器时不能由本仓库生成该闭环的cmd_vel | 明确完整启动拓扑和每条必要输入的生产者；已有外部启动配置应先核对。不能靠猜测补造真实点云配准或执行器 |
| 默认方向校验未放行 | `config/ht.yaml`的ht_directions_calibrated=false；HtCostMap::ready显式要求calibrated=true | 这是有意的运行门槛，不是把false直接改true就解决。需确认模型0°方向、map轴、车体朝向、八通道顺序及车辆参考点的对应关系 |
| 加速度约束未采用真实时间 | follower每次回调用固定dt=0.05限幅；调度间隔并不由这段代码保证为50ms。因此约束的是每次回调增量，不是严格的每秒变化量 | 用单调时钟记录实际发送间隔，明确首次调用和长停顿处理，再按实际dt限幅。例：设0.5m/s²，每步增量0.025m/s，若实际间隔10ms则差分为2.5m/s²。算术反例已验证；不代表实际车体加速度实测 |

`nav2_mode=True`的Fixposition驱动已将odometry_enu的frame设为map，因此这里**没有**把它误判为必然的ENU/map名称错误。仍需确认map、vrtk_link、算法车辆参考点和rslidar之间真实的几何关系；命名相同不证明原点与朝向相同。

## 时序与异常输入逻辑

1. TARE检查里程计的有限位置、四元数范数、坐标系和时龄；地图有过期/未来时间检查，规划与跟踪共用HT约束，跟踪器还复核即将执行的路径和实际候选指令弧线。这些是合理基础。
2. TARE处理已配准点云时使用回调当时的`robot_position_`，没有在该回调内按点云时间戳取对应位姿。仿真常用的state_estimation_at_scan与实车连续定位输出不是同一时间对齐保证。实车入口未显示同步器，因此点云、传感器原点、关键帧位置的一致性尚未证实。若时间差0.2秒、速度0.5m/s，平移差就是0.1m，约2.4个HT格；这是公式示例而非实测误差。
3. follower的里程计回调主要检查有限值，没有和TARE一样检查map坐标及单位四元数。若外部接入错误坐标系，不能指望该回调自动纠正；路径内各PoseStamped与父Path坐标一致性也需要统一约束。
4. 定位回跳/重定位后，历史高程、旧路径及已完成状态没有一套已验证的统一重置流程。TARE对时间戳倒退也未在该回调中作单调丢弃；不能仅凭消息新鲜就认为空间参考仍连续。属于接入前需处理的状态一致性问题。
5. `planXYTheta`及部分ROS参数缺少完整的NaN/Inf与范围检查；例如cell、goal_radius、max_radius等尚未全部覆盖。建议在节点初始化及核心算法入口共享校验，拒绝不合法配置。
6. 完成判定主要依赖TARE全局返航/局部完成及近家低速停留，不等于真实全环境已探索。应明确任务完成口径；当前缺少实车未观测区域/任务数据，不能证明其符合用户现场的完成要求。

以上第2、4、6项的实车严重程度取决于实际输入和任务，未提供真实录包，不能虚构已发生的实车偏移、重定位或误完成。

## 分辨率是否适合实车

| 环节 | 已核对规格 |
|---|---|
| 原始高程与历史处理 | 291×291，float32，配置0.04093567251461988m/格，约11.9123m见方 |
| 模型输入 | `[1,1,291,291]`，NCHW逻辑形状；channels_last仅为内存布局优化 |
| 模型输出 | `[1,8,2,241,241]`；softmax沿两类别维，取可通过类后为8×241×241 |
| 地图/规划输出 | 241×241、约9.8655m见方；保持中心与米/格，每边裁去25格，不是缩放 |
| 原始格与输出格映射 | 输入(r+25,c+25)与输出(r,c)的世界坐标一致；模型51×51感受野约2.0877m |
| RViz显示 | 每3格取样约81×81，仅用于显示；图像分辨率1920×1080不进入HT模型 |

建议先保留现有**291×291输入、241×241输出及原米/格**。依据是现有模型/桥接的确定接口和已验证的中心裁剪映射，不是已经证实它是现场最优分辨率。

不能将同一地形任意缩到更少像素后仅修改resolution：高程差的真实采样尺度、51格感受野覆盖范围和细障碍表达都会改变。也不能靠放大RViz视频解决定位/点云时间错位。32个搜索航向桶不代表模型具有32个独立方向分数；当前仍是八个45°模型方向。

缺少原始完整训练规格、实车标注地形样本、实际高程噪声/缺测分布和现场延迟目标，因此不能确定现场检测精度、方向校准正确性或端到端实时性。合成输入模型形状/计时结果见`model_resolution.json`；这是本机CPU离线结果，不代表目标车载计算平台的速度或实车精度。

另有显示问题：`tare_visualizer.cpp`的Y分辨率误读X参数，非等距视点配置会画错范围；诊断视频对非16:9相机输入仍固定resize到960×540，通用宽高比保真未验证。这两项不改变HT模型输入，但会误导显示判断。

## 尚缺的资料

- 实车实际使用的总launch/启动命令，以及map系点云、高程图和跟踪器是否由外部程序提供。
- 一小段真实录包：定位、已配准点云、原始高程GridMap及其时间戳/坐标系，以及现有TF树和算法参考点定义。
- 模型训练的真实栅格尺度/方向定义，以及现场目标地形的标注或可核对样本。
- 现场要求的处理频率、允许地图/路径时龄；若需要评估执行跟踪，还缺实际命令消费逻辑和运动模型约定。

这些资料缺失时，可以确认上述默认入口不能闭合及代码边界问题；不能进一步承诺“接上设备即可实车正常运行”。修正顺序应为输入链闭合与坐标时间一致→异常状态/时序约束→真实录包的离线算法复核，再讨论是否具备现场运行条件。按用户要求，本轮不再进行仿真实验。
